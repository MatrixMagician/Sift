<objective>
Land the Phase 17 tracer: one production-quality end-to-end slice that takes a
case containing eu-stack dumps and nothing else, runs the deterministic Phase
15/16 analysis that today has zero CLI callers, and writes a Markdown report
plus `eustack_signatures.csv` to `<case>/eustack/` — exiting 0 with no
DSSErrors log anywhere in the case.

Purpose: EUS-09 is the phase's shipping surface and the layer every later plan
expands from. Proving the whole path (store -> dump grouping -> per-dump
analysis -> saturation on the last dump -> renderer -> CSV -> CLI -> exit code)
on one dump first means a wrong seam costs one commit, not five. The multi-dump
generalisation (17-02) and the progression rendering (17-03) then fill in
behaviour without moving any boundary this plan establishes.

Output: `src/sift/pipeline/eustack_progression.py` (dump grouping, ordering,
the frozen bundle model), `src/sift/render/eustack_report.py` (Markdown, JSON,
CSV), the `sift eustack` command in `src/sift/cli.py`, and
`tests/test_cli_eustack.py`.

<assumption_delta_decision>
The deterministic detector reports `detected: false` for phase 17, so this
block is advisory only and blocks nothing.

- **Noun now primary:** the *ordered sequence of dumps*, not *the dump*. Phase
  15/16 analysed one flat event list; from here the case holds N dumps.
- **Decision: promote.** `ProgressionAnalysis` carries `dumps: tuple[DumpSlice, ...]`
  as the general representation, and a single-dump case is rendered as the N=1
  case of it — one entry, `step_deltas=()`, `overall_delta=0`. There is no
  single-dump code path to keep in sync with a multi-dump one.
- **Why not add-alongside:** a `single | multi` branch would have to be kept
  consistent in three places (pipeline, renderer, CSV header width), and 17-03's
  byte-identity gate would then only cover whichever branch the fixture happened
  to take.
- **Suggested (not required) invariant test:** feeding a one-dump case produces a
  `ProgressionAnalysis` with `len(dumps) == 1` and an empty `step_deltas`, and
  feeding the same events split across two identical dumps produces
  `step_deltas == (0, ...)` per signature — the generalised intent, encoded once.
</assumption_delta_decision>

`resolve_dump_order(dumps)` reads `.ts` and `.ts_confidence` off the FIRST event
in each group for which `event.thread is not None`. Do not look for a preamble
event and do not re-scan `Event.raw` with a second timestamp regex: the adapter
copies the dump-time header value onto every thread event
(`adapters/eustack.py:215-223`), which is why one thread event per group is a
sufficient and correct representative. With exactly one dump return
`ORDER_BASIS_SINGLE` and an empty flag tuple. With two or more dumps where every
group's representative has `ts_confidence != "missing"`, sort on the total key
`(ts, source_file)` and return `ORDER_BASIS_TIMESTAMP` with an empty flag tuple
(D-01). The `ts_confidence == "missing"` branch and its flag are 17-02's work —
in this plan raise `NotImplementedError` on that branch rather than silently
falling through to an undeclared order, so a wrong case shape fails loudly
instead of producing an unlabelled ordering.

`analyse_eustack_bundle(events, rules, rules_hash, thresholds)` groups, orders,
runs `analyse_eustack` once per dump in resolved order, sets `analysis` to the
LAST dump's result and `saturation` to `analyse_saturation(last_analysis,
thresholds)` (D-11 — never a union across dumps, never one section per dump),
and builds a `ProgressionAnalysis` whose `dumps` tuple carries one `DumpSlice`
per dump in resolved order. `DumpSlice.ts` is the ISO-8601 string form or `None`
— never a `datetime`, so `model_dump(mode="json")` stays stable. For each
`SignatureGroup` in the last dump's analysis emit one `SignatureProgression`
with `counts` holding that signature's per-dump thread count in resolved dump
order, `step_deltas=()` and `overall_delta=0` when there is one dump, `appeared`
and `vanished` both `False`, `matched_frame` set to `frames[frame_index]` when
`frame_index` is not `None` else `None`, and `leaf_frame` set to `frames[0]` if
`frames` is non-empty else `None` (D-07's display projection — the full `frames`
tuple stays on the model as the cross-dump join key but never reaches the CSV).
Multi-dump delta computation lands in 17-02; a one-dump case's correct answer is
the empty-delta shape above, so nothing here is a placeholder. Sort
`ProgressionAnalysis.signatures` on the explicit total key
`(-counts[-1], frames)`, mirroring `analyse_eustack`'s own sort.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| customer thread dump -> case store | C++ symbol text, library paths and source paths from the customer's binaries enter as untrusted bytes |
| case store -> CSV cell | untrusted symbol text reaches a file opened by spreadsheet software |
| case store -> Markdown report / stdout summary | untrusted symbol text reaches the operator's terminal |
| CLI `case` argument -> bundle directory path | operator-supplied name resolves to a filesystem write target |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-01 | Tampering | `write_eustack_signatures_csv` — matched_frame / leaf_frame / matched_pattern / per-dump `source_file` header cells | high | mitigate | Every string cell AND every per-dump header cell routed through `_csv_safe` imported from `render/perfmon_report.py:203`; sanitise-then-quote ordering preserved by reuse rather than reimplementation (D-06) |
| T-17-02 | Tampering | `render_eustack_markdown` and the CLI stdout summary | medium | mitigate | Every dynamic Markdown cell through `render.markdown._field`; every `print()` of log-derived text through `render._util.sanitise` as `_sanitise`, matching `perfmon()`'s T-13-STDOUTESC handling |
| T-17-03 | Tampering | bundle-dir derivation in `cli.eustack` | medium | mitigate | Bundle dir derived solely from `case_db_path(config.data_dir, case).parent / "eustack"`, whose containment assertion `_case_store` has already validated; no user-supplied path segment is ever joined |
| T-17-04 | Information disclosure | `OSError` handler in `cli.eustack` | low | mitigate | `_sanitise(str(exc))` in the message and `raise typer.Exit(1) from None` so no traceback frame or internal path reaches the operator; asserted by `test_eustack_write_failure_removes_partial_bundle` |
| T-17-05 | Information disclosure | `render_eustack_json` non-ASCII passthrough | medium | mitigate | `ensure_ascii=True` backslash-escapes every non-ASCII code point, so no raw C1 or bidi-override byte survives into the JSON artefact (the T-13-JSONESC control, reused) |
| T-17-06 | Denial of service | CSV width growing with dump count | low | accept | Column count is bounded by the operator's own capture set, which they assembled; inventing a dump cap would silently drop evidence, which is the worse failure for a forensic artefact |
| T-17-SC | Tampering | npm/pip/cargo installs | low | accept | This phase installs no external package — `17-RESEARCH.md` records "No external packages are introduced by this phase" and no `pyproject.toml` change is in scope, so the package-legitimacy checkpoint has no subject |
