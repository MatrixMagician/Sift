<objective>
Convert the dimension mismatch from an unrecoverable wedge into a recoverable
one: `sift analyze --re-embed` drops the `vectors` and `kb_vectors` vec0
tables together, announces exactly what it is discarding, and lets the shipped
lazy-create path rebuild them at the new width — all inside the single
transaction `cluster_and_label` already owns, so an interrupted rebuild rolls
back intact.

Purpose: today a dimension mismatch cannot be resolved short of deleting the
case. This is the recovery path, and it is the only destructive operation in
the phase — it therefore carries the announcement, the transactional
guarantee and the rollback test.
Output: `CaseStore.drop_vector_tables()`, the dimension branch of
`--re-embed`, and the D-09 announcement.
</objective>

<design_deviation_from_research>
RESEARCH.md Open Question 1 recommends **two** single-table methods
(`drop_vectors_table()`, `drop_kb_vectors_table()`) so "the caller pairs them
per D-08, keeping the pairing an explicit decision at the call site".

This plan takes **one** method, `drop_vector_tables()`, deliberately. Method
naming is Claude's Discretion per CONTEXT.md, and three things argue for the
single method:

1. **The pairing is a corruption path, not a preference.** D-08 exists because
   dropping `vectors` alone leaves `kb_vectors` at a stale declared width that
   `CREATE VIRTUAL TABLE IF NOT EXISTS` will silently no-op against. A single
   method makes that mistake structurally impossible; two methods make it
   possible-but-tested. For a corruption path, structural beats conventional.
2. **The `meta.embedding_dim` clear belongs to neither table alone.** The key
   is shared, so a third concern would otherwise need a third method or an
   implicit coupling to one of the two.
3. **It deletes a threat.** Because the method only DROPs two code-constant
   table names and clears meta — recreation is left to the shipped
   `ensure_vectors_table` / `ensure_kb_vectors_table` — the phase introduces
   **no new dimension-interpolating DDL at all**. RESEARCH.md's §Security
   Domain flags SQL injection via an interpolated `dim` in "the new DROP/CREATE
   DDL" as the one applicable V5 concern; under this design there is no new
   CREATE site, so the concern is mitigated by construction rather than by
   convention.
</design_deviation_from_research>

Add `CaseStore.drop_vector_tables(self) -> tuple[int, int]` to
`src/sift/store.py`, placed immediately after `ensure_kb_vectors_table` so the
create/drop pair reads together. It is a CALLER-OWNS-TRANSACTION method like
every other write in this file — its docstring must say so, mirroring
`upsert_vectors`' wording, because `cluster_and_label` calls it inside the one
`store.transaction()` block that owns the whole run.

Behaviour, in order:

1. `self._ensure_vec_loaded()` first — vec0 tables cannot be dropped without
   the extension loaded, and this is the shipped lazy-load convention.
2. Count the rows about to be discarded: `SELECT count(*) FROM vectors` and
   `SELECT count(*) FROM kb_vectors`, each wrapped so a
   `sqlite3.OperationalError` for a missing table yields 0. `count(*)` against
   a vec0 table is already exercised by the shipped
   `tests/test_cluster.py:243`, so no fallback formulation is needed. These two
   integers are the return value and the numbers the D-09 announcement prints.
3. `DROP TABLE IF EXISTS vectors` and `DROP TABLE IF EXISTS kb_vectors`. Both
   names are module-level code constants in the SQL text, never interpolated
   values — introduce no f-string and no parameter into these statements.
   Dropping the primary vec0 name drops all four shadow tables
   (`vectors_info`, `vectors_chunks`, `vectors_rowids`,
   `vectors_vector_chunks00`) together; this was verified empirically against
   the pinned `sqlite-vec==0.1.9` and needs no manual shadow-table cleanup.
4. `DELETE FROM kb_chunks` — the KB namespace must not retain chunks whose
   vectors have just been discarded. `index_kb` already replaces the whole
   `kb_chunks` table on every `--kb` run so nothing is lost that would not have
   been replaced anyway, and clearing it prevents exactly the half-surviving-
   pair inconsistency D-08 exists to prevent.
5. Delete the `embedding_dim` and `embedding_metric` keys from `meta`. This is
   what lets the very next `ensure_vectors_table(new_dim)` see
   `existing is None` and take its create-and-record branch instead of its
   STORE-03 raise branch. Use the store's existing meta write path; if no
   delete helper exists, add the minimal `DELETE FROM meta WHERE key = ?`
   execution inline in this method rather than introducing a general-purpose
   public meta-deletion API.

Do NOT modify `ensure_vectors_table` in any way — not a bypass parameter, not
a `force=` flag, not a reordering. Its `existing is not None and int(existing) != dim`
raise is the STORE-03 contract, `tests/test_store_vectors.py:114` asserts it
verbatim, and weakening it for the rebuild path would weaken it for the
default path too (RESEARCH Pitfall 4). The rebuild works by clearing state
before the guard runs, never by disarming the guard.

Do NOT recreate either table inside this method. `vectors` is recreated
immediately afterwards by the `ensure_vectors_table(dim)` call
`cluster_and_label` already makes; `kb_vectors` is recreated lazily by
`ensure_kb_vectors_table(dim)` on the operator's next `--kb` run, at the new
width, which is what D-08 intends — `index_kb` re-indexes the whole directory
from scratch on every `--kb` run, so the KB regenerates at no extra design
cost. Eagerly recreating an empty `kb_vectors` here would also create the
table on cases that never use `--kb`, a behaviour change nobody asked for.

Add to `tests/test_store_vectors.py`, reusing the shipped `_tables(db)` helper

vector shaped for the ORIGINAL width and asserting it succeeds — an insert at
the new width against a restored old-width table would fail, so a successful
old-width insert is the discriminating evidence.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator intent (`--re-embed`) → destructive DDL | The only path in Sift that deletes persisted analysis artefacts. |
| in-flight transaction → committed `case.db` | The window in which a partial drop could wedge the case. |
| pipeline → operator (stderr) | The channel that discloses the blast radius. |

## STRIDE Threat Register (ASVS L1, block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-03 | Denial of Service | destructive `--re-embed` dimension rebuild dropping `vectors` + `kb_vectors` | **high** | mitigate | Three layers. (1) The blast radius is announced with real counted totals sourced from the drop's own return value, before the transaction commits. (2) Both drops, the `kb_chunks` clear, the meta clear and the recreate happen inside the ONE `store.transaction()` that already owns every write, so a partial drop can never commit — verified empirically on pinned `sqlite-vec==0.1.9` that a mid-transaction rollback restores the original table at its original declared width, and pinned by `test_drop_vector_tables_rollback_restores_original_width`. (3) The path is unreachable without the operator explicitly passing `--re-embed`; the default path still hard-raises STORE-03 and destroys nothing. |
| T-20-04 | Tampering | SQL injection via an interpolated `dim` in new DDL | low | mitigate | Mitigated by construction: `drop_vector_tables` executes only `DROP TABLE IF EXISTS` against two code-constant table names, a `DELETE FROM kb_chunks`, and parameterised meta deletes. No new dimension-interpolating CREATE site exists — recreation reuses the two shipped `ensure_*_table` statements whose `# noqa: S608` justification was already reviewed. Pinned by the acceptance greps counting `FLOAT[` at 2 and `S608` at 3. |
| T-20-05 | Information Disclosure | the D-09 announcement text | low | mitigate | The message is a fixed literal plus four integers (two dimensions, two counts). No store-sourced or server-sourced string enters it, so the T-03-23 "untrusted text never enters a rich renderable" rule is satisfied without `_sanitise`, and the plan 20-02 `markup=False, highlight=False` binding keeps it literal. |
| T-20-10 | Tampering | `kb_vectors` surviving a rebuild at a stale declared width (RESEARCH Pitfall 5) | medium | mitigate | The drop is unconditionally paired inside one method, so `vectors` can never be rebuilt alone; `kb_chunks` is cleared with it. Pinned by asserting `ensure_kb_vectors_table(new_dim)` creates a NEW-width table after the rebuild, not merely that a table exists. |
| T-20-SC | Tampering | package-manager installs | n/a | accept | No package-manager install task in this plan; no change to `pyproject.toml`/`uv.lock`. |
